# 도안보고 웹 전환 및 앱 배포 Phase Plan

작성일: 2026-10-04  
상태: 승인된 웹 뷰어 기능을 구현해 GitHub Pages에 배포했다. 공개 주소와 앱 진입 자산은 응답을 확인했으며, Android 태블릿·사용자 실패 PDF·공개 브라우저 상호작용·Capacitor APK 실기기 검증은 대기 중이다. 상세 증거는 docs/WEB_MIGRATION_CHECKLIST.md를 참고한다.

## 진행 현황 (2026-10-04)

- Phase 0: 기존 기능 범위와 테스트 입력 상태를 기능 체크리스트에 고정했다. 사용자가 겪은 실패 PDF와 실제 Android 태블릿은 아직 검증 대상에 들어오지 않았다.
- Phase 1–3: React + TypeScript + Vite 워크스페이스, PDF.js, IndexedDB 저장, PDF 뷰어, 페이지 관리, 독립 구분 보기와 위치 복원을 구현했다. TypeScript·lint·단위 테스트 및 Edge 자동 브라우저 흐름을 통과했다.
- Phase 3 INDEX 개선: 단일 보기는 작업 캔버스 전체 폭을 쓰고, 모든 페이지 썸네일을 가로 목록으로 제공한다. 진행선 2종과 펜·직선·형광펜·지우개·텍스트, 페이지별 저장·실행 취소/다시 실행을 추가했다. 분할 경계 조절 뒤 PDF 페이지를 debounce해 임시 캔버스에 렌더한다. portable Edge 자동 검사에서 페이지 선택, 필기 실행 취소/다시 실행, 설정 표시, 분할 비율 변경 후 로딩 종료를 확인했다.
- Phase 4: PWA 오프라인 캐시를 구성했다. production preview에서 PDF를 추가하고 뷰어 상태를 저장한 뒤 오프라인 새로고침 후 PDF를 다시 렌더링했다. 이는 Android 태블릿 통과를 뜻하지 않는다.
- Phase 4A: `npm run build:portable`로 `portable/index.html` 단일 파일을 만들고 Edge `file://`에서 실행·PDF 추가·임시 저장 안내·작업 파일 가져오기와 생성 PDF의 뷰어 canvas 렌더 완료를 확인했다. IndexedDB가 막힌 파일 실행에서는 메모리 임시 저장과 `.doanbogo` 백업을 사용한다.
- Phase 5: `https://github.com/blg-mike/doanbogo-web`의 `main`에 `e271402`를 반영하고 GitHub Pages 배포를 완료했다. [공개 웹](https://blg-mike.github.io/doanbogo-web/)의 진입 페이지와 JS·CSS·manifest가 HTTP 200으로 응답한다. 공개 브라우저에서 PDF 조작 시나리오 검증은 남아 있다.
- Phase 6: Phase 5 공개 검증과 Android 태블릿 테스트 뒤 진행한다.

일반 웹 주소에서는 브라우저 IndexedDB에 자동 저장한다. 직접 파일 실행은 IndexedDB가 허용되면 자동 저장하고, 차단되면 메모리 임시 저장과 `.doanbogo` 가져오기·내보내기를 사용한다. 기존 Expo 앱 데이터 자동 이관은 구현 범위에 포함되지 않는다.

## 1. 목표와 기본 결정

현재 구현된 화면과 기능을 React + TypeScript + Vite 웹 프로젝트로 옮겨 브라우저에서 검증한 뒤, 동일한 웹 UI와 PDF 엔진을 Capacitor Android 앱으로 배포한다.

- 웹 프로젝트는 기존 Expo 프로젝트 옆의 `doanbogo-web/`에 별도로 만든다. 기존 `doanbogo-app/`과 APK는 전환 비교 기준으로 보존한다.
- 웹 프로젝트를 독립 Git 저장소로 관리한다. 승인된 계획·현재 기능표를 해당 저장소의 `docs/`에 포함하고 소스·lockfile·배포 workflow를 GitHub에 올린다.
- 화면: 워크스페이스와 PDF 뷰어. 도안 관리·설정·숨김 관리는 부속 모달로 구현한다.
- UI는 DOM/CSS로 옮기고 기존 색상·배치·기능 의미를 유지하면서 태블릿 터치와 데스크톱 마우스/키보드에 맞춘다.
- PDF는 `pdfjs-dist`를 직접 사용한다. API·worker 버전을 맞추고 worker·CMap·기본 글꼴·WASM 자산을 웹 빌드와 portable 단일 HTML에 함께 포함한다. JPEG 2000 이미지는 OpenJPEG WASM으로 해독하고 Pages 하위 경로와 PWA 캐시에서도 자산을 찾도록 한다.
- 웹 저장은 IndexedDB에 PDF Blob과 메타데이터·작업 상태를 저장한다. 문서 식별자는 유지 가능한 ID를 사용하고 일시적인 Blob URL은 영구 저장하지 않는다.
- GitHub Pages는 빌드 결과 `dist/`를 배포한다. 저장소 하위 경로에 맞는 Vite `base`와 해시 경로 `/#/viewer/:id`를 사용한다.
- 사용자 PDF는 브라우저 또는 앱의 로컬 저장소에 보관한다. 서버 계정·업로드·동기화는 추가하지 않는다.
- 우선 검증 대상: Android 태블릿 Chrome과 데스크톱 Chrome/Edge. iPad Safari는 별도 브라우저 검증 결과를 기록하고, 실제 확인 전에는 지원 완료로 표시하지 않는다.
- 첫 앱 배포는 Android 테스트 APK다. iOS 네이티브 배포와 스토어 출시는 이후 별도 출시 단계로 둔다.

## 2. 현재 구현 기능과 이관 범위

소스 확인 기준: `doanbogo-app/src/app/`, `src/components/PdfPane.tsx`, `src/db.ts`. 아래의 구현 여부는 코드 연결 상태이며 실제 기기 통과 여부와 구분한다.

| 영역 | 웹에서 유지할 동작 |
|---|---|
| 워크스페이스 | PDF 추가, 첫 페이지 표지, 표지/목록 보기, 파일명·태그 검색, 최근 실행/이름/업로드순 정렬, 빈 상태·검색 결과 없음 |
| 도안 관리 | 태그 편집, 원본 PDF 공유, 도안 사본 만들기, 도안과 작업 정보 삭제 |
| 설정 | 로컬 저장 방식 안내와 닫기 |
| 기본 뷰어 | 돌아가기·파일명, 이전/다음·페이지 번호 이동, 확대/축소·더블탭, 로딩·오류 |
| 페이지 관리 | 북마크, 전체 페이지 썸네일 탐색, 숨김·복구, 숨김 페이지 건너뛰기, 마지막 보이는 페이지 숨김 방지 |
| 구분 보기 | 같은 문서의 두 영역, 독립 페이지·배율·이동, 활성 영역, 가로는 좌우·세로는 상하 |
| 구분 조절 | 경계선 미리보기와 드래그 종료 후 적용, 25–75% 범위, 가로·세로별 비율 |
| 진행선·필기 | 이동, 펜, 직선, 형광펜, 지우개, 텍스트 주석, 가로·세로 진행선 표시·스타일 설정, 페이지별 실행 취소/다시 실행 |
| 상태 저장 | 최근 열람, 보기·정렬, 페이지 북마크·숨김·썸네일, 양쪽 페이지·배율, 구분 여부·활성 영역·비율, 진행선·필기 설정과 페이지 작업 |

- 도안 복제는 현재와 같이 원본 PDF와 기본 메타데이터를 복제하며 태그·북마크·숨김·작업 위치는 새 문서의 기본 상태로 시작한다.
- 원본 공유는 브라우저가 파일 공유를 지원할 때 공유하고, 그 외에는 원본 PDF 다운로드를 제공한다.
- **웹에서 보완할 현재 미완성 항목:** 양쪽 영역의 실제 확대 중심/이동 위치를 수집하고 새로고침·회전·재진입 후 복원한다. 현재 앱은 정확한 pan 중심을 저장·복원하지 않는다.
- **이번 이관에서 새로 개발하지 않는 항목:** PDF 본문 검색, 선택 페이지 PDF 생성, 계정·동기화. 전체 작업 백업은 portable 빌드 범위에 포함하며 PDF·페이지 작업·필기 상태를 보관한다.
- 기존 Expo 앱 내부 데이터는 브라우저가 자동으로 읽을 수 없다. 기본 전환은 원본 PDF 재가져오기이며 기존 태그·북마크·작업 위치의 자동 이관은 별도 작업이다.

## 3. Phase별 작업

### Phase 0 — 현재 기능과 검증 기준 고정

**목적:** 화면 재작성 과정에서 기능을 누락하거나 미구현 기능을 구현 완료로 착각하지 않도록 기준을 만든다.

- 현재 화면·모달·버튼·저장 항목을 기능표로 고정하고 기존 앱 화면을 비교 자료로 남긴다.
- 사용자 태블릿에서 실패한 정상 PDF, 한글 파일명 PDF, 다중 페이지 PDF, 큰 PDF, 회전 페이지 PDF를 검증 목록에 등록한다. 실제 파일이 없는 항목은 준비 전으로 기록한다.
- 구현됨/부분 구현/계획만 있음과 소스 확인/브라우저 확인/태블릿 확인을 별도 열로 관리한다.

**산출물:** 이관 체크리스트와 테스트 문서 목록.  
**완료 기준:** 위 범위표의 모든 동작에 대응 화면과 확인 시나리오가 있으며, 실제 실패 PDF 재검증이 최종 완료 조건에 들어 있다.

### Phase 1 — 웹 기반과 PDF·저장 기술 검증

**선행 조건:** Phase 0.  
**목적:** 전체 UI를 옮기기 전에 PDF 선택→표시→저장→재열기 흐름과 두 영역의 독립 동작을 확인한다.

- React + TypeScript + Vite 프로젝트, 기본 CSS 토큰, 워크스페이스/뷰어 해시 경로, lint·typecheck·build 스크립트를 구성한다. Expo 전용 의존성은 웹 프로젝트로 가져오지 않는다.
- 파일 선택 결과를 PDF.js로 실제 열어 페이지 수와 렌더 가능 여부를 확인한다. MIME/확장자는 선택 안내로 사용하고 정상 파일을 단순 헤더 검사만으로 거절하지 않는다. 파일 접근 실패·파싱 실패·암호 요구를 구분한다.
- 문서 메타데이터와 PDF Blob을 같은 IndexedDB 트랜잭션에 저장하고 ID로 다시 읽는다. 작업 상태도 IndexedDB에 저장하며 스키마 버전 변경은 데이터 보존 migration으로 처리한다.
- PDF 읽기/저장과 화면 코드를 분리하는 작은 저장 모듈을 둔다. 네이티브 파일 경로나 Expo SQLite 호출을 UI에 남기지 않는다.
- PDF.js 문서 로드는 공유하고 두 영역은 별도 canvas·페이지·배율·중심점·입력 상태를 갖도록 검증한다. 같은 페이지를 양쪽에 띄우는 경우도 검사한다.
- `navigator.storage.estimate()`는 브라우저 저장 한도 추정치로 사용한다. 조회 불가만으로 등록을 차단하지 않고 실제 `QuotaExceededError`를 저장 한도 초과로 안내한다. 지속 저장 요청이 거절돼도 정상 흐름으로 처리한다.

**산출물:** 동작하는 웹 기반과 PDF/IndexedDB 검증 결과.  
**완료 기준:** 로컬 웹과 저장소 하위 경로의 production preview에서 PDF가 열리고, 브라우저 재실행 후 저장된 PDF를 다시 열 수 있다. 두 영역을 조작해도 다른 영역의 상태가 바뀌지 않는다. 이 조건이 실패하면 전체 화면 이관을 완료로 진행하지 않는다.

참고: [PDF.js 공식 예제](https://mozilla.github.io/pdf.js/examples/), [저장 한도 추정](https://developer.mozilla.org/en-US/docs/Web/API/StorageManager/estimate), [지속 저장 요청](https://developer.mozilla.org/en-US/docs/Web/API/StorageManager/persist).

### Phase 2 — 워크스페이스와 도안 관리 이관

**선행 조건:** Phase 1의 PDF 저장·재열기 통과.  
**목적:** 현재 워크스페이스 전체를 웹에서 사용할 수 있도록 만든다.

- PDF 추가 버튼, 첫 페이지 표지, 표지/목록 보기, 검색·정렬, 태그 편집, 최근 열람 시각과 설정 모달을 연결한다.
- 표지 이미지를 작게 생성·재사용하고 목록의 모든 PDF를 고해상도로 동시에 렌더하지 않는다.
- 사본 만들기·원본 공유/다운로드·삭제 확인을 구현한다. 삭제는 PDF와 해당 문서의 모든 작업 상태를 하나의 저장 작업으로 정리한다.
- 중복 가져오기 실행을 방지하고 선택 취소, 빈 파일, 읽기 실패, 브라우저 저장 한도 초과, 저장 후 목록 갱신 실패를 각각 처리한다.
- 설정 문구를 “이 브라우저에 저장”으로 바꾸고 브라우저 데이터 삭제 시 자료가 지워지는 조건을 안내한다.

**산출물:** 웹 워크스페이스와 관리 모달.  
**완료 기준:** 추가→검색/태그→정렬/보기 변경→복제→원본 다운로드→삭제가 동작하고 새로고침 후에도 목록·태그·선호도가 유지된다. 다운로드한 원본 PDF의 바이트가 바뀌지 않는다.

### Phase 3 — PDF 뷰어·페이지 관리·구분 보기 이관

**선행 조건:** Phase 1의 두 영역 기술 검증과 Phase 2.  
**목적:** 기존 뷰어 동작을 유지하고 웹에서 실제 작업 위치까지 복원한다.

- 기본 뷰어 헤더, 이전/다음·전체 페이지 썸네일 이동, 확대 범위 1–5배·더블탭, 로딩·실패·재시도를 연결한다. 손가락 pinch/pan과 마우스 조작을 PDF 영역에서 처리한다.
- 북마크·숨김·숨김 관리 모달을 연결한다. 숨김 변경 시 양쪽 영역을 각각 보이는 페이지로 보정하고 마지막 보이는 페이지는 숨길 수 없도록 한다.
- 활성 영역과 독립 뷰포트, 가로 좌우/세로 상하 배치, 25–75% 경계선 미리보기, 방향별 비율, 단일/구분 전환을 구현한다.
- 새 문서에서 두 영역 보기의 기본 비율은 현재 영역 65%·보조 영역 35%로 두고, 사용자가 조정한 기존 비율은 재진입 시 복원한다.
- 단일 보기에서는 작업 캔버스를 남은 폭 전체에 맞추고 페이지를 가운데 배치한다. 하단 썸네일은 모든 페이지를 보여 주며 숨긴 페이지는 흐리게 표시하고 선택하면 복구 후 연다.
- 페이지 좌표 기준의 가로·세로 진행선을 표시하고 선별 표시·색상·굵기·투명도를 조정한다. 진행선 위치와 설정은 문서에 저장한다.
- 펜·직선·형광펜·텍스트를 추가·편집·이동하고 지우개로 지운다. 페이지 단위 실행 취소/다시 실행은 편집 세션당 최대 100개 동작을 보관한다.
- 분할 경계 드래그는 패널 크기를 즉시 미리보기하고, PDF 페이지 재렌더는 120ms 동안 크기가 멈춘 뒤 수행한다. 이전 프레임은 새 프레임이 준비될 때까지 유지하고 오래된 작업과 제한 시간 초과를 처리한다.
- 양쪽 `page + zoom + normalized center`를 실제 좌표로 저장한다. 창 크기·방향 변경과 구분모드 전환 후 같은 PDF 위치를 복원한다.
- 문서별 최신 snapshot을 순서대로 저장한다. 일반 조작은 500ms debounce, 제스처 종료·숨김 변경·뷰어 종료에서는 즉시 저장한다. 브라우저 종료 이벤트 하나에 저장을 맡기지 않는다.
- 페이지 썸네일은 화면 근처에서 최대 2개씩 렌더한다. 빠른 페이지 전환·확대에서는 이전 렌더 작업을 취소하고, 뷰어 종료 시 canvas·문서 핸들·일시 URL을 해제한다.
- 진행선·필기 데이터는 IndexedDB v2의 페이지 작업 저장소에 기록한다. `.doanbogo` 백업은 v2로 내보내며 v1 백업을 계속 가져올 수 있다.

**산출물:** 웹 뷰어, 구분 보기, 위치 저장·복원.  
**완료 기준:** 같은 PDF의 1p/3p를 양쪽에서 독립 조작하고, 회전·분리 비율 변경·새로고침·브라우저 재실행 후 각 영역의 페이지·배율·중심 위치가 복원된다. 단일 보기는 전체 작업 캔버스를 쓰고 전체 썸네일에서 페이지를 선택할 수 있다. 진행선·필기 상태가 저장되고 실행 취소/다시 실행·지우개가 동작하며, 분할 경계 조절 뒤 로딩이 종료된다. 같은 페이지의 북마크·숨김 상태는 양쪽에 반영된다.

### Phase 4 — 브라우저 통합 검증과 오프라인 사용

**선행 조건:** Phase 2·3.  
**목적:** 태블릿에서 실제 PDF 작업을 지속할 수 있는지 검증한다.

- production build로 워크스페이스→뷰어→구분 보기→북마크/숨김→재실행→복원→원본 다운로드 흐름을 검사한다.
- 터치 영역·포커스·키보드·모달 닫기·가로/세로·작은 화면을 실제 브라우저에서 확인한다. 자동 검사는 저장 트랜잭션과 뷰포트 복원·구분 상호작용 등 핵심 회귀에 한정한다.
- 사용자 실패 PDF, 큰 PDF, 한글명, 암호 PDF, 잘못된 파일, 저장 한도 초과를 검사한다. 암호 요구를 손상·공간 부족으로 표시하지 않는다.
- 두 영역 동시 렌더, 연속 확대·페이지 전환, 회전·문서 열고 닫기 반복에서 canvas·worker·URL 해제와 메모리 증가를 확인한다.
- `vite-plugin-pwa`로 앱 화면·PDF worker·필요 자산을 캐시한다. PDF와 작업 상태는 IndexedDB가 보관한다. 업데이트는 저장 중인 작업을 강제로 새로고침하지 않도록 다음 안전한 진입에 적용한다.

**산출물:** 브라우저별 검증표, 실패 항목 수정, 오프라인 재진입 가능한 웹 빌드.  
**완료 기준:** Android 태블릿에서 실제 실패 PDF가 추가·표시되고 작업 상태가 복원된다. 한 번 온라인으로 로드한 후 오프라인 재실행에서도 저장된 PDF를 사용할 수 있다. 미확인 기기·브라우저는 검증 완료와 구분해 기록한다.

참고: [Vite PWA 가이드](https://vite-pwa-org.netlify.app/guide/).

### Phase 4A — 서버 없이 단일 HTML 직접 실행

**선행 조건:** Phase 1–3 웹 기능 구현. 이 분기는 GitHub Pages/PWA와 Android 태블릿 공개 검증을 대신하지 않는다.  
**목적:** 사용자가 파일 관리자나 탐색기에서 배포용 `index.html`을 직접 열 수 있게 한다.

- `npm run build:portable`은 Vite 소스 진입점과 구분해 `portable/index.html`을 만든다. JavaScript·CSS·PDF.js 처리 모듈은 HTML 내부에 포함하고, 파일 URL에서 worker/CORS 요청을 만들지 않도록 PDF.js를 메인 스레드에서 실행한다.
- PWA/service worker/manifest 등록은 이 빌드에서 제외한다. 해시 라우팅과 현재 워크스페이스·뷰어 기능은 유지한다.
- 실행 초기에 IndexedDB 열기와 간단한 쓰기·읽기를 확인한다. 접근이 차단되거나 오류가 나면 메모리 임시 저장으로 전환하고 지속 저장 상태를 화면에 표시한다. quota 초과는 임시 저장 가능 오류와 구분한다.
- 설정에서 버전 필드가 있는 `.doanbogo` ZIP 백업을 내보내고 가져온다. v2 백업에는 PDF·표지·태그·페이지 플래그·뷰어 위치·표시 설정·진행선·필기 작업을 보관하고 v1 백업은 빈 페이지 작업으로 읽는다. 가져오기는 자료 전체를 검증한 후 반영하고 ID 충돌은 새 ID로 이관한다.
- 저장이 임시 모드일 때는 워크스페이스에 경고와 작업 파일 저장 버튼을 표시한다. README는 루트 `index.html`을 직접 열지 말고 빌드된 파일을 열도록 안내한다.

**현재 확인:** Edge `file://` 단일 HTML 시작, 생성한 2페이지 PDF 파싱·표지 생성, IndexedDB 차단 후 임시 저장 표시, `.doanbogo` 가져오기와 ID 이관을 자동 확인했다. Android 파일 실행과 사용자 실패 PDF는 미검증이다.

**완료 기준:** 지원 브라우저에서 네트워크·서버 없이 단일 파일을 열고 PDF를 표시한다. IndexedDB가 막혀도 자료 손실 위험을 사용자에게 표시하고 작업 파일 내보내기·가져오기로 다른 실행 위치에서 복원한다.

### Phase 5 — GitHub 업로드와 GitHub Pages 공개 검증

**선행 조건:** Phase 4의 핵심 시나리오 통과, 사용할 GitHub 저장소 URL 확정. 웹 저장소 연결과 첫 Pages 배포는 완료했다.
**목적:** 공유 가능한 검증 웹 주소와 재현 가능한 배포 경로를 만든다.

- 웹 저장소에 소스·lockfile·실행 문서·검증표를 올린다. 개인 PDF·로컬 DB·서명 키·APK 빌드 출력은 저장소에 넣지 않는다.
- GitHub Actions에 의존성 설치→typecheck/lint→핵심 검사→Vite build→Pages 배포를 연결한다.
- 확정한 저장소명에 맞춰 `base`·PWA scope·worker 및 자산 경로를 적용하고 해시 경로로 뷰어 새로고침을 지원한다.
- 실제 공개 URL에서 빈 브라우저 초기 진입, PDF 추가, 뷰어 직접 경로/새로고침, 오프라인 재진입, 새 버전 적용 후 데이터 유지를 확인한다.
- README에 배포 URL, 로컬 실행 명령, 브라우저 저장 범위, 지원·미검증 환경을 기록한다.

**산출물:** GitHub 소스 저장소, 배포 workflow, 실제 웹 URL.  
**완료 기준:** Actions 배포 성공뿐 아니라 공개 웹에서 PDF·worker·모든 화면이 정상 로드된다. 배포 도메인이나 브라우저가 바뀌면 기존 로컬 자료가 자동 공유되지 않는다는 점을 문서에 남긴다.

참고: [Vite GitHub Pages 배포 문서](https://vite.dev/guide/static-deploy.html#github-pages).

### Phase 6 — 검증된 웹을 Capacitor Android APK로 배포

**선행 조건:** Phase 5 공개 웹의 핵심 작업 흐름 통과.  
**목적:** 동일 웹 화면을 설치형 앱에서 실행하고 기기 저장·공유 기능을 연결한다.

- 웹 프로젝트에 Capacitor Android를 추가한다. `webDir`은 `dist`를 사용하고 웹 자산을 APK에 내장한다. 원격 Pages 주소를 항상 열어야만 실행되는 구조로 만들지 않는다.
- Pages 배포용 하위 경로 설정과 앱 내장용 자산 경로를 빌드 모드로 구분한다. 앱에서는 서비스워커를 사용하지 않고 내장 자산으로 실행한다.
- Phase 1의 저장 모듈 뒤에 네이티브 저장 구현을 연결한다. PDF는 앱 전용 파일 저장소에, 메타데이터·작업 상태는 SQLite에 보관한다. 사용할 Capacitor SQLite 연동은 착수 시 지원 버전과 Android 호환성을 확인하고 lockfile에 고정한다.
- 시스템 파일 선택, PDF.js가 읽을 수 있는 로컬 파일 URL, 원본 공유·삭제를 연결한다. 대용량 PDF를 반복해서 base64로 복사하는 경로는 실제 메모리 사용을 확인하고 줄인다.
- 첫 내부 테스트 APK는 기존 Expo 앱과 별도 패키지로 설치한다. 기존 설치본의 데이터가 Capacitor로 자동 이전된다고 가정하지 않는다. 기존 패키지를 대체하는 배포는 데이터 이관과 서명을 확정한 뒤 별도로 진행한다.
- 실제 Android 태블릿에서 PDF 추가→작업→강제 종료→복원→오프라인 실행→공유를 검증하고 서명된 테스트 APK를 전달한다.

**산출물:** 웹 기반 Android 프로젝트, 재현 가능한 APK 빌드 문서, 테스트 APK와 기기 확인 결과.  
**완료 기준:** 네트워크 연결 없이 앱이 실행되고 실제 사용자 PDF가 추가·표시되며 작업 위치가 앱 재시작 후 복원된다. APK 빌드 성공과 실기기 기능 통과를 구분해 보고한다.

참고: [Capacitor 웹 프로젝트 연결](https://capacitorjs.com/docs/getting-started), [네이티브 파일 저장](https://capacitorjs.com/docs/apis/filesystem), [저장 방식 안내](https://capacitorjs.com/docs/guides/storage).

## 4. 순서·첫 작업·최종 완료 기준

`Phase 0 → Phase 1 → Phase 2 → Phase 3 → Phase 4 → (Phase 4A 로컬 파일 배포 / Phase 5 Pages 공개) → Phase 6`

- 첫 작업은 Phase 0의 현재 기능표와 검증 PDF 목록 확정이다. 이어서 PDF 추가·두 영역 표시·IndexedDB 재열기를 먼저 검증한다.
- Phase 3에 추가 승인된 진행선·필기 기능은 웹 INDEX에서 먼저 검증하고, 이후 앱 구현은 사용자가 별도로 요청할 때 시작한다.
- GitHub 소스 업로드, Pages 공개 성공, 공개 브라우저 통과, Capacitor APK 생성, 실제 태블릿 통과를 각각 별도 상태로 기록한다.
- 최종 완료는 기존 구현 기능의 웹 이관 체크리스트가 모두 통과하고, 공개 웹과 새 Android 앱에서 사용자 PDF의 실제 작업 흐름이 확인된 상태다.
- 실제 사용자 PDF와 태블릿, GitHub 저장소 URL은 해당 검증·공개 단계의 외부 준비 조건이다. 준비되지 않은 항목은 완료로 표시하지 않는다.

## 6. PDF.js JPEG 2000 렌더링 검증 기록

2026-10-04에 PDF.js가 JPEG 2000 이미지 해독에 필요한 OpenJPEG WASM을 찾지 못해 일부 PDF 페이지의 이미지가 빈 상태로 표시되는 문제를 수정했다. CMap·기본 글꼴·WASM 자산을 일반 웹 빌드와 portable 단일 HTML에서 공급하고, Pages 하위 경로의 OpenJPEG 대체 자산과 PWA 캐시를 연결했다. 이미지 해독 실패 시에는 페이지 번호가 포함된 오류를 표시한다.

제공된 15페이지 PDF를 Edge `file://` portable 실행과 GitHub Pages 공개 주소에서 각각 추가했다. 두 환경 모두 9페이지 도안이 표시됐고, PDF.js 전체 페이지 검사에서 이미지 해독 실패가 없었다. Actions 배포와 공개 URL HTTP 200, 브라우저 console/page error 없음도 확인했다. PDF 파일은 저장소에 추가하지 않았다. Android 태블릿 실기기 확인은 남아 있다.
